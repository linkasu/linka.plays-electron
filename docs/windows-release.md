# Windows-релиз с сохранённым лаунчером

Публичный комплект 3.0.0 заменяет Unity на Electron, но сохраняет отдельное
окно «LINKa запуск», ярлыки на него и URL `/linkaplay/linkaplaysetup.exe`.
Требуется Windows 10 1809+ или Windows 11 x64. Данные пользователей и неиспользуемые
файлы Unity автоматически не удаляются; перенос формата настроек Unity не заявляется.

## Упаковка

`resources/electron/installer.iss` использует прежний Inno AppId
`{D17098DB-EAFA-4EFF-A280-65E1CFBAE428}`. Electron устанавливается как
`LINKa.plays.exe`, рядом — self-contained .NET 10/WPF лаунчер и `version.json`.
При обновлении сохраняется предыдущий, в том числе нестандартный, каталог.
Ярлыки ведут на лаунчер; `linka-play://game/<id>` ведёт непосредственно в Electron.
Лаунчер запускает EXE относительно собственного каталога. Проверка обновлений
не блокирует окно и ограничена пятью секундами; без сети игры доступны.

Windows Electron-updater отключён. Версия стабильного комплекта должна быть
числовой и выше предыдущей (Unity: 2.0.0); beta не попадает в публичный манифест.
Тестовые Electron 0.1.x обновляются ручной установкой полного комплекта.

## Ошибка `latest.yml` в установленной 3.0.0

Если внутри Windows-игры появляется `Cannot find latest.yml` со ссылкой на
`v3.0.1`, это ошибка Electron-updater, а не лаунчера. В исходниках тега
`v3.0.0` Windows-проверка уже отключена. До переустановки нужно сверить путь
реально запущенного EXE, цель ярлыка и `version`/`buildSha` в упакованном
`resources/app.asar/package.json`: один номер версии не доказывает совпадение сборок.
Не удалять старую установку и настройки для диагностики.

Публичная 3.0.0 содержит Inno-комплект и `launcher.zip`, но не NSIS `latest.yml`.
Не добавлять такой манифест для Inno-установщика: это несовместимые способы обновления.
Проверенный полный комплект устанавливается после завершения игры; переход
со старой NSIS-установки нельзя считать проверенным только по тесту Inno → Inno.

Release CI отдельно проверяет переход с настоящего опубликованного установщика
3.0.0, SHA-256 `36b305ce8047bf4035326a2a58d9f639ffc17a042173e40f9909018b541ecc08`,
на новый комплект в нестандартном каталоге. Проверяются файл-маркер пользователя,
ярлык, протокол, версия и запуск установленного EXE. Это не проверка переноса
всех реальных пользовательских настроек или физического Tobii.
Сценарий запускается на отдельном Windows runner, чтобы не затронуть установленное приложение:

```powershell
./scripts/ci/windows-installer-smoke.ps1 -Installer <candidate.exe> -PreviousVersion 3.0.0
```

Packaged smoke сверяет версию и CI commit через настоящий preload, направляет
Electron-updater на локальный HTTP-сервер и запрещает любые обращения к нему
на Windows, в том числе в `UPDATE_TEST_MODE=1`. При нарушении сохраняются
отчёт, журнал процесса и скриншот.

В новых сборках техническая ошибка не показывается поверх игры; уведомление
закрывается мышью, клавиатурой или взглядом. Подробности Electron-updater
пишутся в `updater.log` внутри Electron `userData`; `UPDATE_LOG_PATH` переопределяет путь.
На Windows этот журнал не создаётся отключённым Electron-updater.

## Кандидат и приёмка

1. Игровая основа 3.0.0 — `e0a590e008ae49885102767d82835a5d5d584933`.
   Зафиксировать итоговый SHA с изменениями доставки. Commit лаунчера закреплён
   в `.github/workflows/release.yml`; исходники доступны в `linkasu/LINKa.plays-launcher`.
2. Запустить `release.yml` на нужном ref с `version=3.0.0`, `publish=false`.
   Это собирает кандидат без публичного релиза и изменения сайта.
3. CI проверяет typecheck, unit, publisher, layout, readiness, TTS, packaged
   privacy/window, затем настоящий Unity setup с закреплённым SHA-256 → новый
   setup в старом каталоге, сохранение файла пользователя/ярлыка/протокола и
   чистую установку. .NET 6 в CI нужен только старому установщику, не новому.
4. На Windows проверить именно этот артефакт: лаунчер, запуск из чужого CWD,
   понятную ошибку при отсутствии игрового EXE без закрытия лаунчера и реальное
   Electron-окно. Проверить PNG, а не только CDP JSON. Игры с Tobii проверяются
   отдельно от CI, который использует `LINKA_NO_TOBII=1`.
5. Установщик не подписан сертификатом разработчика; предупреждение Windows
   не является основанием отключать Defender/UAC.

## Публикация

После приёмки публиковать проверенные артефакты по новому неизменяемому тегу
в **linkasu/linka.plays-windows-releases**, отдельно от исходников и старого
Electron updater-feed. Не заменять файлы уже выпущенного GitHub Release.
Комплект содержит только Inno EXE и `launcher.zip`, без NSIS `latest.yml`.
Одного `--latest=false` недостаточно: Windows 0.1.22 и старые beta принудительно
включают `allowPrerelease`, выбирают 3.x из Atom-ленты и получают 404 манифеста.
При ручном `publish=true` workflow
заново собирает и проверяет комплект; для публикации уже принятого кандидата
использовать скачанные CI-артефакты без повторной сборки. Автоматическая публикация
в отдельный репозиторий требует явно настроенного `WINDOWS_RELEASE_TOKEN`.
Без этого секрета запускать `publish=false`, после приёмки публиковать локальным
`gh` с существующим доступом: персональный токен не копировать в secrets неявно.

`publish-linka-plays-updater.yml` получает точную версию и запускает на сервере
`scripts/publish-windows-release.mjs`. Он проверяет release tag, stable-статус,
имена артефактов, размер и SHA-256 из GitHub; блокирует параллельную публикацию
и понижение версии. Сначала проверяются оба скачанных файла, затем создаётся
резервная копия, заменяются установщики и `launcher.zip`, и лишь затем
оба `version.json`. Атомарна замена одного файла, не всего HTTP-комплекта.
Транзакционный журнал и проверяемый rollback защищают от частичного сбоя;
незавершённое восстановление блокирует повторную публикацию.

Старое зеркало принадлежит другому системному пользователю. Публикация использует
уже настроенный `sudo -n` SSH-аккаунта, включая полный путь к Node из его окружения;
права каталогов и sudoers не меняются. Для ручного запуска:
`sudo -n "$(command -v node)" /home/aacidov/linka-docker/release-tools/<source-sha>/linka-plays-publish.mjs <version>`.

Пути относительно `/home/aacidov/linka-docker/wordpress/`:

- `linkaplay/linkaplaysetup.exe`, `linkaplay/version.json`, `linkaplay/launcher.zip`;
- `dist/linka.plays/linka.plays.setup.exe`, `dist/linka.plays/version.json`;
- `linkaplay/archive/` — предыдущие публичные комплекты;
- `linkaplay/archive/unity-2.0.0-setup.exe` — неизменяемый CI fixture,
  SHA-256 `344b39997ebda4a1cf13211b200f06aaf590149704d341a81cbd4ca5f8593381`.

Перед изменением WordPress сохранить БД. На `/play` убрать только ссылку
Унгуряну (сам EXE оставить), указать Windows 10/11 x64 и сохранённый лаунчер.
Проверить публичные манифесты, SHA-256 обоих URL и скачанный с сайта setup.
При откате новых загрузок восстановить точную резервную копию; уже установленную
3.0.0 исправлять выпуском 3.0.1, не объявлять 2.0.0 её обновлением.

## Проверка кандидата 3.0.0

Проверенный CI-артефакт собран из `4b7bdea04fa1b75c3bc16619ce6faece5cb3fd06`.
На Windows 11 подтверждены развёрнутое игровое окно, сохранённый лаунчер,
`deviceFound=true`, `tracking` и свежие точки реального Tobii. Аудит 2048 на
800×600 и 1024×600 обнаруживает кнопки направлений 74–78 вместо рекомендованных
88 CSS px. На 1600×900 размер достаточен. Счётчик HUD-overlap этого аудитора
также включает кнопки внутри самой HUD-панели; его ненулевое значение само по
себе не доказывает перекрытие игрового поля. Полная зелёная CDP-проверка всех
разрешений не заявляется.

## Восстановление старых NSIS-установок

Фраза «Не удалось проверить обновление» сама по себе не определяет причину.
До переустановки получить ОС, полную ошибку, версию/build SHA, путь реально
запущенного EXE и цель ярлыка. Windows 0.1.22 и beta.95 воспроизводят
`ERR_UPDATER_CHANNEL_FILE_NOT_FOUND` на `v3.0.1/latest.yml`; beta.99, beta.102
и 3.0.0 уже отключают Windows Electron-updater в исходниках.

Разделение будущих релизов не изменяет уже установленные старые клиенты.
Не удалять старые GitHub Releases и не добавлять `latest.yml` со ссылкой на Inno.
Безопасный ручной путь, который проверяет отдельный CI job:

1. Завершить игру и сохранить копию каталога старой установки и её Electron
   `userData` (обычно `%APPDATA%\linka.plays-electron`; путь сверить с установленной
   сборкой). Резервная копия должна быть вне каталога установки.
2. Через штатное удаление Windows удалить только старую NSIS-программу, не данные.
   Не использовать флаг `--delete-app-data`.
3. Установить проверенный полный Inno-комплект. Сохранить выбранный каталог.
4. При необходимости вернуть собственные пользовательские файлы из резервной
   копии; не копировать поверх новой программы старые EXE, DLL и `app.asar`.
5. Проверить настройки, новый ярлык на лаунчер, запуск игр, протокол
   `linka-play`, версию и build SHA. Старый updater больше не должен запускаться.

Это **не автоматическая установка Inno поверх NSIS**. Сохранность произвольных
сторонних файлов без резервной копии не гарантируется. Старую копию не удалять
до подтверждения успешного перехода.

CI проверяет настоящие SHA-256-pinned NSIS 0.1.22/beta.95 в стандартном
и нестандартном каталоге на отдельных Windows runners. Скрипт
`scripts/ci/windows-nsis-migration-smoke.ps1` намеренно запрещён вне GitHub Actions:
он не является утилитой миграции для пользовательского компьютера.

## Приёмка доставки 3.0.2+

До публикации обязательны:

- `node --test scripts/ci/updater-feed-compatibility.test.cjs`;
- `node --test scripts/publish-windows-release.test.mjs`;
- `node --test scripts/ci/verify-public-windows-release.test.mjs`;
- `node scripts/ci/assert-windows-release-assets.mjs <accepted-directory> <version>`;
- Windows CI: Unity → Inno, 3.0.0 → кандидат, NSIS → ручное восстановление;
- packaged smoke с реальным preload и PNG из установленного приложения.

Проверенные исходники, SHA лаунчера и принятый CI run указываются в release notes.
Публиковать только EXE и ZIP этого run. Затем запустить workflow
`publish-linka-plays-updater.yml` на том же source ref с точной версией.
Он доставляет publisher в каталог source SHA, не перезаписывает общий `update.js`,
сериализует публикации и запускает публичную проверку:

```bash
node scripts/ci/verify-public-windows-release.mjs 3.0.2
```

Проверка полностью скачивает оба EXE и ZIP, сравнивает размер и SHA-256 с точным
GitHub Release и повторно читает оба манифеста. Одного HTTP 200 или HEAD недостаточно.
Отчёт сохраняется как CI artifact.

При аварии не удалять lock/журнал вслепую: сначала убедиться, что publisher уже
не работает, проверить backup и записанную фазу. Если автоматический rollback
не завершился, восстановить все пять файлов из проверенного backup, сверить хеши,
и только после этого разбирать блокировку. Откат сайта не понижает уже установленную
версию: для этих пользователей выпускается следующая большая версия.
